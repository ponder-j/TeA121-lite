## 2. 已经实现的完整分析链路

```text
C / C++ / LLVM IR
    ↓
Clang/LLVM 15 生成 IR
    ↓
opt -passes=mem2reg 规范化
    ↓
tea121-extract 提取 MiniIR
    ↓
Python 抽象解释：区间 + 指针基址 + 字节偏移 + 栈对象
    ↓
alloca/GEP/load/store 和库函数模型检查
    ↓
Alarm / Diagnostic / CFG / Block State / Trace
    ↓
CLI JSON/Text，或后端导入后供 Web 工作台展示
```

主要入口和职责如下：

| 模块 | 文件 | 当前职责 |
|---|---|---|
| C/LLVM 前端 | `analyzer/src/tea121/frontend.py` | 编译 C、执行 `mem2reg`、调用提取器、记录规范化 IR |
| LLVM 提取器 | `analyzer/llvm-extractor/extractor.cpp` | LLVM 指令、CFG、DebugLoc、DataLayout、全局字符串转 MiniIR |
| MiniIR 加载 | `analyzer/src/tea121/ir/loader.py` | 检查版本和基本结构 |
| 抽象域 | `analyzer/src/tea121/domain/` | Interval、PointerValue、MemoryObject、State |
| 求解器 | `analyzer/src/tea121/analysis/solver.py` | worklist、状态转移、边界检查、函数摘要 |
| 库模型注册 | `analyzer/src/tea121/analysis/models.py` | 已知函数名、输入函数和纯函数分类 |
| 结果构造 | `analyzer/src/tea121/report/result.py` | 版本化结果、告警、诊断、CFG 和 trace |
| CLI | `analyzer/src/tea121/cli.py` | `tea121 analyze ... --format json/text --mode normal/trace` |
| Juliet runner | `analyzer/tools/evaluate_juliet.py` | 编译、链接、提取、分析、四态分类、JSON/CSV 汇总 |

## 3. 具体实现到了哪一步

### 3.1 LLVM 提取和 MiniIR

已实现：

- LLVM 15 Docker 环境，包含 `clang-15`、`llvm-link-15`、`opt-15` 和 `tea121-extract`。
- 从 LLVM API 提取函数、基本块、前驱/后继、终结指令和 DebugLoc。
- 提取 `alloca`、常量 GEP、变量 GEP、`load`、`store`、`icmp`、`phi`、部分二元运算和调用。
- 提取全局变量大小、全局字符串长度和字符串内容。
- MiniIR 顶层包含 `schema_version`、`llvm_version`、`target_triple`、`data_layout`。
- 未知 LLVM 指令降级为 `unsupported` 节点，不会被静默删除。

尚不完整：

- `loader.py` 只检查 `schema_version` 和 `functions` 是否为数组，没有真正加载 JSON Schema 做完整校验。
- 复杂多级 GEP、位运算、整数转换、全局数组、常量表达式、结构体字段等尚未完整建模；提取器对部分指令直接标为 `unsupported`。
- Docker 固定 LLVM 15，但没有显式固定目标 triple；当前容器实测 triple 为 `aarch64-unknown-linux-gnu`，跨主机架构复现时需要注意。
- C++ 提取器缺少独立的 CTest/映射回归目录。

### 3.2 抽象域和状态

已实现：

- `Interval = Bottom | [lower, upper] | Top`。
- `join`、`meet`、`widen`、有限精度加减乘、固定位宽溢出时退化为 `Top`。
- `PointerValue` 支持多基址、字节偏移区间和 unknown base。
- `MemoryObject` 支持大小区间、分配位置和 `escaped` 标记。
- 全局字符串长度摘要和按 `(memory_object, byte_offset)` 保存的最小标量内存摘要。
- 分支边上的基础比较精化，以及不可达状态的 Bottom 表示。

限制：

- `State` 只有 `join` 和整数 `widen`，没有完整的 `State.meet`、指针/对象/字符串域 widen 或 narrowing。
- `icmp` 的比较区间主要精确处理 `eq/ne`、部分 `<` 和 `>=`；`sle/sgt` 等谓词仍可能退化为 `[0,1]`，边精化覆盖不完整。
- 多基址指针按基址集合 join，未实现一般 alias analysis 或路径敏感指针分析。
- 标量内存只跟踪单对象、单字节偏移的常量摘要；聚合值、结构体和数组元素级内存都需要继续扩展。

### 3.3 CFG、循环和过程内分析

已实现：

- 前向 worklist，按基本块合并入口/出口状态。
- `alloca`、GEP、load/store 的转移和访问宽度检查。
- `icmp`、`phi`、`select`、`copy` 和加减乘转移。
- 配置化的 widening 触发轮数，默认 `widen_after=3`。
- 输出的 `block_states` 保存每个块入口/出口状态。
- 当前工作区新增 `cfg_nodes`，可输出每个基本块中的指令文本、指令 op、DebugLoc、终止指令和源码行，用于 Web CFG 工作台展示。

限制：

- 没有实现任务书要求的 widening 后一轮 narrowing。
- PHI 语义仍偏“值 join”，不是完整的按前驱边分别选择 incoming value。
- 循环头的路径约束和复杂归纳变量精度不足，容易产生漏报或误报。
- 没有针对重复访问和重复诊断的去重策略，循环多次访问时可能出现重复 alarm key/诊断。

### 3.4 函数间和 split-file

已实现：

- 用户函数调用时绑定形参、执行被调函数并回填返回值。
- `max_call_depth=8`，递归调用和超深调用产生保守 `unknown_effect` Diagnostic。
- 函数摘要按“函数名 + 调用点”缓存，具备最小调用点区分能力。
- Juliet runner 能处理 `51a/51b` split-file：分别生成 IR，再用 `llvm-link-15` 链接后归一化、提取和分析。

限制：

- 没有显式 `context_depth=1` 配置项；当前行为只是调用点级别的近似实现。
- 只回填返回值和返回指针，不会把被调函数对调用者状态的副作用完整回传。
- 复杂调用图、间接调用、递归摘要和跨多函数的指针逃逸仍未完成。
- 直接 `tea121 analyze file.c` 前端仍是单 C/C++ 文件；多文件能力目前主要由 Juliet runner 提供。

### 3.5 库函数和输入模型

已接入或部分实现：

| 函数 | 当前行为 | 成熟度 |
|---|---|---|
| `memcpy` | 目标宽度按长度参数检查 | MVP |
| `memmove` | 复用拷贝长度检查 | MVP |
| `memset` | 复用写入宽度检查 | MVP |
| `strcpy` | 仅当源为已知全局字符串时精确计算“内容长度 + NUL” | MVP，覆盖窄 |
| `strncpy` | 按常量 `n` 检查目标对象 | 部分，未完整建模截断/NUL 语义 |
| `fgets` | 按最大读入字节数检查 | 部分 |
| `recv` | 按最大接收长度检查并传播 `[-1, n]` 返回值 | 部分 |
| `fscanf` | 数字转换按固定标量宽度；字符串转换保持 unknown | 部分，格式和别名处理不完整 |
| `strlen` / `wcslen` | 已知全局字符串长度可返回精确值，否则 Top | 部分 |
| `atoi` / `rand` / socket 等 | 作为纯/观察调用传播 Top 或返回摘要 | 部分 |

未知调用会将传入指针对象标记为 `escaped` 并产生 `UNKNOWN_CALL`，而不是当作 clean。

主要缺口：

- 行为仍硬编码在 solver 的 `_call_model` 中，`LibraryModelRegistry` 目前主要是名字注册，不是完全解耦的 `FunctionModel` 实现。
- 五个必需模型的“安全、确定越界、可能越界、未知语义”四态测试尚未逐一补齐。
- 宽字符、`wcscpy/wcsncpy`、局部字符串、动态字符串摘要和输入别名仍不足。
- `fscanf` 的 `%lf/%lld/%hd`、抑制符、宽度和指针别名尚未完整建模。

### 3.6 告警、诊断和结果契约

Alarm 已包含：

- stable 形式的 `alarm_key`、`memory_object_id`。
- detector/rule pack/CWE/family/violation kind。
- `definite | possible` severity。
- 函数、基本块、指令、原始指令文本和源码位置。
- 对象大小区间、偏移区间、访问宽度、安全条件和原因列表。

Diagnostic 已包含：

- `unknown_effect`、`unsupported`、`error` 三类 severity。
- `code/message/impact/location` 等字段。
- 未支持指令、未知调用、未知长度、递归、超深调用等显式降级。

当前结果 JSON 已包含任务书要求的主要顶层结构：

```text
schema_version
run_id
analyzer_version
detector_id / detector_version
rule_pack_id / rule_pack_version
status / summary
inputs / config
alarms / diagnostics
artifacts / cfg / cfg_nodes
block_states / trace
```

仍需收敛：

- Alarm 还没有任务书中提到的结构化 `evidence` 字段，当前主要靠 `reason/source_location/safe_condition` 解释。
- 结果 schema 对 `cfg_nodes`、`block_states`、trace 等内部对象约束较松；`scripts/check_analyzer_contract.py` 是字段 sanity check，不是完整 JSON Schema 验证。
- `inputs` 对直接 C 输入没有源文件 SHA-256；SHA-256 目前主要用于 Juliet runner 和规范化 IR artifact。
- `config` 没有记录模型开关、`max_call_depth`、调用上下文和完整工具链命令。
- normal 模式输出规范化 IR artifact，但没有同时输出原始 C 源码 artifact。
- `unknown_effect` 不会自动把顶层 `status` 改成 `unsupported`；Juliet runner 会将其归为 unsupported，但其他消费者若只看 `status + alarms` 有误判为 clean 的风险。
- 未看到对“同输入重复运行语义结果完全稳定”的自动测试。

- Web 工作台已支持 CFG、状态检查、源码和告警/诊断展示；当前未提交修改正在增强 CFG 的 IR 可读性。

### 3.8 数据库存储内容

后端使用 SQLite 保存平台状态和分析结果。数据库不是把分析器 JSON 原样塞进一个表，而是围绕一次 **AnalysisRun** 拆成项目、源码、任务、结果和评估五组数据；所有告警、诊断、CFG、状态、trace 和 artifact 都归属于具体 Run。

```text
Project
 ├─ SourceFile
 ├─ AnalysisRun ── RunFile ── SourceFile
 │    ├─ Alarm
 │    ├─ Diagnostic
 │    ├─ RunArtifact
 │    ├─ CfgNode / CfgEdge
 │    └─ TraceEvent
 └─ Evaluation ── EvaluationCase ── bad/good AnalysisRun
```

| 数据组 | 主要表 | 存储内容 |
|---|---|---|
| 项目与源码 | `projects`、`source_files` | 项目基本信息；源码路径、语言、完整内容、SHA-256、大小和文件版本 |
| 删除审计 | `file_audit_records` | 已删除文件的路径、哈希和删除时间 |
| 分析能力 | `detectors`、`rule_packs` | 检测器、规则包版本及其支持的 CWE、family 和 violation kind |
| 分析运行 | `analysis_runs`、`run_files` | Run 状态、配置、模式、版本、进度、时间和输入文件的多对多关系 |
| 漏洞结果 | `alarms` | 告警位置、严重度、函数/指令、对象大小、偏移区间、访问宽度、安全条件和原因 |
| 未决语义 | `diagnostics` | `unknown_effect`、`unsupported`、`error` 及其位置和影响 |
| 分析产物 | `run_artifacts` | 规范化 LLVM IR 等内容及 SHA-256 |
| 图与状态 | `cfg_nodes`、`cfg_edges` | 基本块、控制流边、块内指令、源码行，以及入口/出口抽象状态 |
| 执行轨迹 | `trace_events` | 指令序号、执行前后状态和解释 |
| 评估结果 | `evaluations`、`evaluation_cases` | 数据集、筛选条件、总体指标，以及 bad/good Run 配对和四态分类 |

完整字段、外键和基数关系见[附录 A](#附录-a数据库表结构明细)。其中 `config_json`、`state_json`、`reason_json`、`evidence_json`、`summary_json` 等字段使用 JSON 文本保存，便于在稳定关系模型之外扩展配置、证据和指标。讲解时可以概括为：

> 数据库不仅保存“发现了什么”，还保存“为什么发现、在哪里发现、基于哪个源码版本、能否复现”。源码和运行是主索引，告警、诊断、CFG、抽象状态、trace 与 IR 产物都围绕 Run 组织，评估模块再把 bad/good Run 配对成四态结果。

# 附录 A：数据库表结构明细

## A.1 基本约定

- 数据库默认位置：开发配置为 `sqlite:///./tea121.db`；Docker Compose 使用 `sqlite:////workspace/data/tea121.db`。
- 数据访问：SQLAlchemy 2.x ORM；启动时通过 `Base.metadata.create_all` 建表，并开启 SQLite `PRAGMA foreign_keys=ON`。
- 主键：绝大多数表使用 36 位 UUID 字符串；`run_files` 使用复合主键。
- 时间：`created_at`、`started_at`、`finished_at` 等由 Python 层生成 UTC 时间。
- JSON 字段：字段名以 `_json` 结尾的列实际存储 JSON 文本，不是 SQLite 原生 JSON 类型。
- 当前 ORM 定义 **15 张业务表**；实际数据库还可能包含 Alembic 自己的版本表。
- 需要注意：`detector_id`、`rule_pack_id`、部分 `source_file_id` 是逻辑关联或版本快照，并不都建立了数据库外键。

## A.2 表之间的连接关系

```text
projects
  ├─1:N─ source_files
  ├─1:N─ analysis_runs
  │        ├─N:M─ source_files         通过 run_files
  │        ├─1:N─ alarms
  │        ├─1:N─ diagnostics
  │        ├─1:N─ run_artifacts
  │        ├─1:N─ cfg_nodes
  │        ├─1:N─ cfg_edges
  │        └─1:N─ trace_events
  └─1:N─ evaluations
           └─1:N─ evaluation_cases
                    ├─N:1─ analysis_runs    通过 bad_run_id
                    └─N:1─ analysis_runs    通过 good_run_id

detectors
  └─1:N─ rule_packs

file_audit_records
  └─ 逻辑上属于 projects，但 project_id 没有数据库外键
```

### 真正的数据库外键

| 子表.字段 | 父表.字段 | 删除行为 |
|---|---|---|
| `source_files.project_id` | `projects.id` | CASCADE |
| `rule_packs.detector_id` | `detectors.id` | CASCADE |
| `analysis_runs.project_id` | `projects.id` | CASCADE |
| `run_files.run_id` | `analysis_runs.id` | CASCADE |
| `run_files.source_file_id` | `source_files.id` | CASCADE |
| `alarms.run_id` | `analysis_runs.id` | CASCADE |
| `diagnostics.run_id` | `analysis_runs.id` | CASCADE |
| `run_artifacts.run_id` | `analysis_runs.id` | CASCADE |
| `cfg_nodes.run_id` | `analysis_runs.id` | CASCADE |
| `cfg_edges.run_id` | `analysis_runs.id` | CASCADE |
| `trace_events.run_id` | `analysis_runs.id` | CASCADE |
| `evaluations.project_id` | `projects.id` | CASCADE |
| `evaluation_cases.evaluation_id` | `evaluations.id` | CASCADE |
| `evaluation_cases.bad_run_id` | `analysis_runs.id` | SET NULL |
| `evaluation_cases.good_run_id` | `analysis_runs.id` | SET NULL |

核心删除规则可以概括为：

- 删除项目，会级联删除源码、分析运行、评估及它们的结果。

- 删除评估，会级联删除评估案例。
- 删除被评估引用的 Run，不会删除评估案例，而是把对应 `bad_run_id` 或 `good_run_id` 置空。

## B.2 分析器如何判断“安全/不安全”

边界检查器只有在能够证明**整个访问区间**都位于对象内时才静默：

```text
安全 = 偏移下界 >= 0
       且偏移上界已知
       且偏移上界 + 访问宽度 <= 对象最小尺寸
```

如果不能证明安全：

- 如果能证明某个可能值已经越界，则输出 `definite`。
- 如果只说明“不能证明安全”，则输出 `possible`。
- 偏移为 Top 时，无法给出具体越界下标，因此通常只能是 `possible`。

这解释了两个核心现象：

- `buffer[10]` 的偏移和对象大小都是精确常量，所以能报 `definite`。
- 循环变量经过 widening 后上界变成正无穷，只能报 `possible`。

## B.3 逐项目解释

### 1. `test_direct_stackoverflow_unsafe`

源码：

```c
int main() {
    char buffer[10];
    buffer[10] = 'H';
    return 0;
}
```

数据库证据：

- 对象：`main/v0`。
- 对象大小：`[10,10]`。
- GEP 偏移：`[10,10]`。
- 访问宽度：1。
- 结论：`10 + 1 > 10`，访问区间 `[10,11)` 越过对象 `[0,10)`。
- severity：`definite`。
- 源码位置：line 3。
- block：`bb0`。

向老师解释：

> 这是一个完全常量化的直接越界。对象大小、下标和访问宽度都能精确确定，所以分析器不仅报警，还能把判定升级为 definite。

### 2. `test_loop_unsafe`

源码：

```c
int buffer[10];
for (int i = 0; i <= 10; i++) {
    buffer[i] = i + 1;
}
```

真实程序语义：

- `i = 0..9` 时合法。
- `i = 10` 时偏移为 40 字节。
- 写入 4 字节，实际范围是 `[40,44)`。
- 对象只有 40 字节，因此确实越界。

数据库结果：

- severity：`possible`。
- 对象大小：`[40,40]`。
- 访问宽度：4。
- 告警 offset：未知（JSON 中 lower/upper 为 null）。
- 源码位置：line 4。
- block：`bb2`。

原因：

- 分析器没有精确跟踪“第 10 次循环”这一事实。
- widening 后 `.0` 的上界变成正无穷。
- GEP 偏移变成 Top，因此不能证明实际越界下标，只能保守报告 `possible`。

向老师解释：

> 这个项目确实是真阳性，但目前不是“精准定位式检测”。它靠保守的 may-analysis 报出可能越界，尚未把 `i=10`、offset=40 这一事实精确还原出来。

### 3. `test_loop_safe`：当前唯一明确的假阳性

源码：

```c
int buffer[10];
for (int i = 0; i <= 9; i++) {
    buffer[i] = i + 1;
}
```

真实程序语义：

- `i` 最大为 9。
- 最大字节偏移为 36。
- 写入 4 字节，范围最大为 `[36,40)`。
- 对象为 `[0,40)`，因此程序安全。

数据库结果：

- severity：`possible`。
- 对象大小：`[40,40]`。
- 访问宽度：4。
- 告警 offset：Top。
- 源码位置：line 4。
- block：`bb2`。

误报发生链：

1. 循环头使用 LLVM `icmp sle`，即 `i <= 9`。
2. 当前 `_refine_cmp` 支持部分 `<`、`>=`、`=`，但没有实现 `sle` 的 true 边精化。
3. 因此进入循环体时没有把状态收紧为 `i <= 9`。
4. 循环进行若干轮后触发 widening，`i` 的区间由 `[0,2]` 变成 `[0,+∞]`。
5. GEP 的 offset 随之上浮为 Top。
6. `_check_access` 无法证明 `offset + 4 <= 40`，于是报 `possible`。
7. 该告警在 worklist 的中间轮次已经写入结果；后续状态即使不再扩展，告警也不会被撤回或重新验证。

这不是源码越界，而是**循环边约束缺失 + widening 过早 + 中间状态直接产生告警**共同造成的保守误报。

向老师解释：

> 安全循环和不安全循环在当前抽象里都被放宽成了 `i ∈ [0,+∞]`。由于 `<=` 的 true 边没有做区间精化，分析器丢失了“最多只能到 9”这个关键证明，最终只能把“无法证明安全”报告成 possible。

### 4. `test_loop_br_safe`

源码：

```c
int buffer[10];
for (int i = 0; i <= 10; i++) {
    if (i >= 10) {
        break;
    }
    buffer[i] = i + 1;
}
```

真实程序语义：

- `i = 10` 时先执行 `break`，不会写 `buffer[10]`。
- 进入写操作的 `i` 最大为 9。
- 因此程序安全。

数据库结果：

- 0 Alarm。
- 0 Diagnostic。
- store 所在块 `bb4` 的入口抽象状态中，offset 为 `[0,8]`。
- 对象大小 `[40,40]`，访问宽度 4。
- `[0,8]` 最大扩展到 `[0,12)`，仍在对象内，所以静默是正确的。

向老师解释：

> 这个样例在真正 store 前增加了一个 break 守卫。到达 store 的抽象偏移仍然是有界的 `[0,8]`，边界检查能够证明最终写入落在 40 字节对象内，因此不报警。

## B.4 为什么会出现误报

### 原因 1：比较谓词精化不完整

循环边界由 LLVM `icmp` 表示，但当前边精化只覆盖部分谓词。`sle` 未处理，导致 `i <= 9` 和 `i <= 10` 在进入循环体时看不到差异。

### 原因 2：循环 widening 过早

当前 `widen_after=3`。经过有限几轮后，上界直接提升到无穷：

```text
[0,2] → [0,+∞]
```

这样虽然能保证循环分析终止，但会迅速损失精度。

### 原因 3：缺少 narrowing

widening 后没有用循环条件重新收缩区间，因此没有机会从 `[0,+∞]` 恢复到 `[0,9]` 或 `[0,10]`。

### 原因 4：告警发生在收敛过程中

当前实现是在每个 worklist 轮次的指令转移中直接追加 Alarm。中间轮次出现的 Top 即使后来被更精确状态覆盖，旧 Alarm 也不会撤销。

### 原因 5：告警原因描述不够具体

`test_loop_safe` 的 reason 写的是“access width exceeds object bounds”，但真实情况是“offset 上界未知，无法证明安全”。这会让老师误以为分析器已经证明了越界。

## B.5 最小验证实验

在不修改仓库的前提下，临时给 `sle` 增加 true 边精化，结果为：

| 项目 | 原结果 | 临时补丁结果 |
|---|---|---|
| `test_loop_safe` | 1 possible | 0 Alarm |
| `test_loop_unsafe` | 1 possible | 仍为 possible，offset 收紧为 `[0,40]` |
| `test_loop_br_safe` | 0 Alarm | 临时出现 possible Alarm |
| `test_direct_stackoverflow_unsafe` | 1 definite | 仍为 definite |

这说明：

- 补齐 `<=` 确实能消除当前安全循环的误报。
- 但只补一个谓词会让其他路径重新失去精度。
- 必须完整实现有符号/无符号比较的 true/false 边精化，并配合最终状态检查和后一轮 narrowing。
- 不能根据项目名或文件名为 `test_loop_safe` 写特判。
